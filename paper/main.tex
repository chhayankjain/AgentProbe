% Abstract

\abstract{
LLM-based intelligent agents are increasingly deployed in production, yet their fault tolerance is poorly understood. We present AgentProbe, an open-source fault-injection and observability toolkit with a five-category failure taxonomy, configurable injectors, and OpenTelemetry tracing. We compare three frameworks---LangGraph, LangChain, and AutoGen---using Llama~3.1 8B via Ollama in a two-phase study. Phase~1 (1{,}050~runs) reveals that AutoGen never invokes tools due to a legacy API-parameter mismatch silently ignored by Ollama. Phase~2 patches AutoGen and re-executes 450~runs (30 per condition; the four fault types share a single seed and produce identical LangGraph/LangChain failure/recovery patterns, so these cells are not independent replications) with matched injection probability ($p = 0.20$) and answer-presence grading. Under injection, LangGraph and LangChain exhibit a 23.3\% error rate [95\%~Wilson~CI: 11.8--40.9\%] with 71.4\% recovery. AutoGen achieves 0\% error rate---its conversation protocol absorbs tool exceptions---but the expected answer string appears in only 33.3\% of assessable baseline questions versus 100\% for LangGraph/LangChain ($n = 12$ each; Llama~3.1 figure uses the historical answer extractor---see Section~7.7). A qualification experiment with guaranteed injection ($p = 1.0$) validates the pipeline via linked traces. Cross-model validation on Mistral~7B and Qwen2.5~7B shows consistent framework-level patterns across three architectures on one local backend. These results show that pass/fail metrics can hide silent tool bypass and error absorption, making fault injection with trace-level observability essential for evaluation.
}

\section{Introduction}\label{sec:introduction}
% ============================================================================

Intelligent agents---autonomous software entities that perceive their environment and act to achieve delegated goals---have been a central thread in AI research since at least the 1950s~\cite{wooldridge2009introduction}. The agent-oriented paradigm, consolidated in the mid-1990s, characterizes agents by autonomy, reactivity, proactivity, and social ability~\cite{wooldridge1995intelligent}. The Beliefs--Desires--Intentions (BDI) architecture became the dominant model for rational decision-making, grounding agent behavior in practical reasoning~\cite{rao1995bdi}.

Large Language Models (LLMs) have given rise to a new generation of agents. These \emph{AI agents} use LLMs as reasoning engines, interleaving reasoning with action execution through architectures like ReAct~\cite{yao2023react} and Chain of Thought prompting~\cite{wei2022chain}. Unlike symbolic BDI agents, they derive their capabilities from statistical patterns learned during pre-training---gaining flexibility but introducing failure modes that have no formal characterization.

Deployment of these agents in production has accelerated rapidly. Frameworks like LangGraph~\cite{langgraph2024}, LangChain~\cite{langchain2023}, and AutoGen~\cite{wu2023autogen} let developers build multi-agent systems that coordinate tool use, retrieval-augmented generation (RAG), and inter-agent communication. But how reliable are these systems under adverse conditions? Production incident reports point to recurring patterns: API timeouts cascading through agent loops, context overflow triggering hallucinated histories, and orchestration deadlocks in multi-agent handoffs. Systematic methodologies for reproducing and comparing these failures across frameworks remain scarce, and to our knowledge no existing open-source toolkit combines runtime fault injection with distributed tracing for LLM agent evaluation.

We address this gap with three contributions:

\begin{enumerate}
  \item \textbf{A failure taxonomy for LLM-based agents.} We propose a five-category classification of failure modes observed in production agent systems: tool call faults, orchestration errors, context degradation, latency anomalies, and output consistency violations (\Cref{sec:taxonomy}).

  \item \textbf{The \agentprobe{} toolkit.} We present an open-source Python toolkit that provides configurable fault injectors for four injectable categories (consistency violations are detected, not injected), an observability layer built on OpenTelemetry~\cite{opentelemetry2024} for distributed tracing and metrics collection, and standardized benchmark tasks for reproducible evaluation (\Cref{sec:system}).

  \item \textbf{A comparative empirical study.} We apply \agentprobe{} in a two-phase experiment to evaluate three prominent agent-oriented frameworks---LangGraph, LangChain, and AutoGen---under controlled fault injection, revealing an integration-level silent failure in Phase~1 and characterizing error-absorption behavior and answer-presence gaps after patching in Phase~2 (\Cref{sec:experiments,sec:results}).
\end{enumerate}

\Cref{sec:related} reviews related work. \Cref{sec:taxonomy} presents the failure taxonomy. \Cref{sec:system} describes \agentprobe{}'s architecture. \Cref{sec:experiments,sec:results} detail the experimental methodology and results. \Cref{sec:discussion} discusses implications for agent design, and \Cref{sec:conclusion} concludes with future directions.

\section{Related Work}\label{sec:related}
% ============================================================================

\subsection{Agent-Oriented Architectures: From BDI to LLM Agents}

The BDI model~\cite{rao1995bdi} provides a theoretical foundation for rational agency based on mental attitudes. Implementations like Jason~\cite{bordini2007programming} and JACK~\cite{winikoff2005jack} showed that symbolic agent architectures work in multi-agent settings. They benefit from formal verification but struggle with the flexibility that open-domain environments require.

LLM-based agents shift the paradigm from symbolic to sub-symbolic reasoning. ReAct~\cite{yao2023react} showed that LLMs can interleave reasoning traces with action execution; Chain of Thought prompting~\cite{wei2022chain} showed that explicit reasoning steps improve task performance. Modern frameworks operationalize these ideas: LangGraph provides stateful graph-based orchestration, LangChain offers composable chain abstractions, and AutoGen enables conversational multi-agent coordination~\cite{wu2023autogen}.

Despite their flexibility, LLM-based agents lack the formal guarantees of BDI architectures. Several authors have argued for integrating symbolic and sub-symbolic approaches~\cite{wooldridge2009introduction,garcez2023neurosymbolic}. Our experiments show concretely where sub-symbolic agents break down, providing data that can inform the design of such hybrid systems.

\subsection{Reliability and Fault Injection}

Fault injection has a long history in distributed systems, from hardware fault simulation~\cite{hsueh1997fault} to chaos engineering as popularized by Netflix's Chaos Monkey~\cite{basiri2016chaos}. Tools like Chaos Toolkit~\cite{chaostoolkit2024} and Gremlin provide programmable fault injection for microservices.

Applying these ideas to AI systems is comparatively new. Prior work has focused on adversarial robustness of neural networks~\cite{goodfellow2015explaining} and test-time perturbations~\cite{ribeiro2020beyond}. Fault injection at the \emph{system level}---targeting the tools, orchestration logic, and infrastructure that surround the LLM---has received little attention. \agentprobe{} addresses this by injecting faults at the agent-system boundary rather than at the model level. ToolEmu~\cite{ruan2024toolemu} takes a complementary approach, using an LLM to emulate tool execution in a sandbox for safety evaluation; it targets risk assessment rather than resilience under infrastructure faults.

\subsection{LLM Evaluation and Benchmarking}

Benchmarks for LLM capabilities have proliferated---MMLU~\cite{hendrycks2021measuring}, HumanEval~\cite{chen2021evaluating}, AgentBench~\cite{liu2023agentbench}---but they focus on task correctness under ideal conditions. Newer agent benchmarks like $\tau$-bench~\cite{yao2024tau}, WebArena~\cite{zhou2024webarena}, and the Berkeley Function Calling Leaderboard~\cite{patil2025bfcl} use realistic environments, yet to our knowledge none inject faults systematically to test resilience.

{\color{magenta}Concurrently, Cemri et~al.~\cite{cemri2025mast} introduce MAST, an empirically grounded taxonomy of 14 multi-agent failure modes derived from 1{,}600+ annotated traces across seven MAS frameworks. Zhang et~al.~\cite{zhang2025failure} address the complementary problem of automated failure attribution in multi-agent systems. Their taxonomy emphasizes inter-agent coordination failures, complementing our taxonomy's focus on tool-call and infrastructure faults.}

On the observability side, LangSmith, Weights \& Biases, and OpenLLMetry~\cite{openllmetry2024} provide tracing and logging for LLM systems.

{\color{magenta}More recently, several concurrent efforts have begun addressing agent resilience directly. Gupta~\cite{reliabilitybench2026} introduces ReliabilityBench, which evaluates LLM agent reliability across consistency, robustness to perturbations, and fault tolerance under controlled tool/API failures, testing two models (Gemini~2.0 Flash, GPT-4o) across four domains. Iannillo et~al.~\cite{mcpinjector2026} provide MCP-Injector, a protocol-aware fault-injection middleware for Model Context Protocol stacks, and show in a 1{,}350-cell experiment that faults cause a 60\% drop in task-completion scores across two backbone sizes and three agent stacks. Mazumder and Lia~\cite{mazumder2026agentcheck} present AgentCheck, a reproduce--intervene--mitigate workbench for LLM agents over MCP. Jia et~al.~\cite{jia2026masfire} introduce MAS-FIRE, a fault-injection and reliability-evaluation framework for LLM-based multi-agent systems. Kraishan~\cite{kraishan2026loud} studies fault detection and recovery in tool-using agents, distinguishing loud (exception-raising) from quiet (silently incorrect) failure modes and finding that agents over-trust plausible but wrong tool outputs.}

{\color{magenta}\agentprobe{} shares the fault-injection motivation with these efforts but differs in three respects: (1)~it uses OpenTelemetry-based distributed tracing to link injected faults to their downstream effects through span IDs, going beyond aggregate metrics; (2)~it evaluates multiple agent frameworks (LangGraph, LangChain, AutoGen) under the same seeded per-call injection mechanism and tracing infrastructure; and (3)~it is fully open-source with both injector and observer exposed as composable Python modules. ReliabilityBench and MCP-Injector do not provide OpenTelemetry integration; Kraishan focuses on detection/recovery taxonomy rather than cross-framework comparison.}

\section{Failure Taxonomy}\label{sec:taxonomy}
% ============================================================================

We organize LLM agent failures into five categories, drawn from production incident reports, framework documentation, and community discussions. Each category targets a distinct surface in the agent-system architecture.

\subsection{Tool Call Faults}

Tool call faults occur at the boundary between the agent and external services. They are the most common failure mode in practice, since agents typically depend on multiple tools (search engines, databases, code executors) that can fail independently.

\begin{itemize}
  \item \textbf{API Timeout:} The external service does not respond within the expected time window, causing the agent to block or retry indefinitely.
  \item \textbf{Malformed Output:} The tool returns a response that does not conform to the expected schema, causing parsing failures or incorrect downstream reasoning.
  \item \textbf{Rate Limit:} The external service throttles requests, forcing the agent to handle backpressure or degrade functionality.
  \item \textbf{API Error:} The service returns an error response (e.g., HTTP 5xx), requiring the agent to decide between retry, fallback, or graceful termination.
\end{itemize}

\subsection{Orchestration Errors}

Orchestration errors arise in the control flow logic governing agent execution, especially in multi-agent systems where coordination adds complexity.

\begin{itemize}
  \item \textbf{Infinite Loop:} The agent enters a cycle of repeated actions without making progress toward the goal, often caused by ambiguous termination conditions.
  \item \textbf{Wrong Branch:} In graph-based orchestration, the agent follows an incorrect execution path due to faulty routing logic or misinterpreted state.
  \item \textbf{State Corruption:} Shared state between agents or between execution steps becomes inconsistent, leading to incorrect behavior.
  \item \textbf{Missing Handoff:} In multi-agent systems, a required handoff between agents fails to occur, leaving tasks incomplete.
\end{itemize}

\subsection{Context Degradation}

Context degradation stems from the finite context window of LLMs and the difficulty of maintaining coherent state across long interactions.

\begin{itemize}
  \item \textbf{Window Overflow:} The accumulated context exceeds the model's maximum token limit, causing truncation of earlier information that may be critical for task completion.
  \item \textbf{Lost State:} Important information from earlier in the conversation is effectively forgotten, even when technically within the context window, due to attention dilution.
  \item \textbf{Hallucinated History:} The agent fabricates events or tool results that never took place, confabulating a history that diverges from reality.
\end{itemize}

\subsection{Latency Anomalies}

Latency anomalies do not cause outright failures but can degrade usability and reliability in production.

\begin{itemize}
  \item \textbf{P99 Spike:} Tail latency increases dramatically for a subset of requests, often due to complex reasoning chains or large context processing.
  \item \textbf{Cascading Delay:} A slow response from one component propagates through the agent pipeline, amplifying the total response time.
  \item \textbf{Cold Start:} Initial requests after deployment or scaling events experience significantly higher latency.
  \item \textbf{Jitter:} Response times exhibit high variance, making it difficult to set appropriate timeouts and SLAs.
\end{itemize}

\subsection{Output Consistency Violations}

Output consistency violations reflect the non-deterministic nature of LLM-based agents: identical inputs may produce semantically different outputs across runs.

\begin{itemize}
  \item \textbf{Non-deterministic Outputs:} Given the same input and tool responses, the agent produces different final answers or takes different action sequences across runs, complicating testing and validation.
\end{itemize}

\Cref{tab:taxonomy} summarizes the taxonomy with the number of sub-types per category and the corresponding \agentprobe{} component that addresses each.

\paragraph{Scope of the empirical evaluation.} {\color{magenta}The taxonomy is a theoretical contribution intended to guide future fault-injection research across all five categories. The experiments in this paper evaluate only the \emph{tool call faults} category (four sub-types), which we prioritize because tool calls are the primary interaction boundary between agents and external systems and the most common failure surface reported in production incident discussions. Injectors for orchestration errors and context degradation are implemented in the toolkit but have not been experimentally validated; the latency injector is implemented but was not used in the experiments (latency differences are observed as a byproduct of fault injection rather than independently controlled); and output consistency is detected by a lexical-divergence classifier only. \section{System Architecture}\label{sec:system}
% ============================================================================

\agentprobe{} is a modular Python toolkit with three layers: fault injection, observability, and benchmarking.

\subsection{Fault Injection Layer}

The fault injection layer provides four injector modules, one for each injectable failure category (consistency violations are detected but not injected, as they arise from inherent model non-determinism).

Each injector wraps a target component (e.g., a tool function) and injects failures with configurable probability $p \in [0, 1]$. Probabilistic injection allows statistical analysis across many runs while keeping failure patterns realistic. Every call is logged with the tool name, injection decision, any resulting exception, call latency, and a linked OpenTelemetry span ID.

\begin{lstlisting}[caption={Example: Injecting tool call failures with configurable probability.},label={lst:injector}]
from agentprobe.injector.tool_failure import (
    ToolFailureConfig, ToolFailureType, ToolFailureInjector,
)

config = ToolFailureConfig(
    failure_type=ToolFailureType.TIMEOUT,
    failure_probability=0.3,
    timeout_seconds=5.0,  # default is 30.0
)
injector = ToolFailureInjector(config)

# Wrap an existing tool function
@injector.wrap
def search_web(query: str) -> str:
    return api_client.search(query)
\end{lstlisting}

\paragraph{Tool Failure Injector.}
Simulates API timeouts (via \texttt{time.sleep} followed by \texttt{TimeoutError}), malformed-output exceptions (via \texttt{ValueError}), rate-limit responses (via \texttt{RateLimitError}), and generic API errors. All four sub-types raise Python exceptions at the tool-call boundary; none injects corrupted data into the agent's context. The ``malformed output'' label describes the simulated \emph{cause} (a garbled upstream response), but the agent experiences it as an exception, making its effect equivalent to the other fault types. We note this scope limitation and discuss its implications in \Cref{sec:discussion}.

\paragraph{Orchestration Failure Injector.}
Injects infinite loop conditions (by manipulating termination flags), wrong branching (by altering routing decisions), state corruption (by modifying shared state dictionaries), and missing handoffs (by dropping inter-agent messages).

\paragraph{Context Failure Injector.}
Simulates context window overflow (by padding the context with filler tokens), lost state (by selectively removing earlier messages), and hallucinated history (by inserting fabricated tool results).

\paragraph{Latency Failure Injector.}
Introduces controlled delays to simulate P99 spikes (large random delays), cascading slowdowns (progressively increasing delays), cold start latency (high initial delay that decreases), and jitter (random delay variance).

\subsection{Observability Layer}

The observability layer provides distributed tracing and metrics collection via OpenTelemetry~\cite{opentelemetry2024}:

\paragraph{Tracer.}
The \texttt{AgentTracer} class instruments agent execution with OpenTelemetry spans, capturing:
\begin{itemize}
  \item Tool call invocations, arguments, and return values
  \item LLM API calls with token counts and latency
  \item Orchestration transitions (state changes, agent handoffs)
  \item Injected failures (type, timing, and recovery outcome)
\end{itemize}

Traces are exported via OTLP (OpenTelemetry Protocol) to backends such as Jaeger for visualization and analysis. For offline validation, an \texttt{InMemorySpanExporter} captures spans as serializable records with trace IDs, span IDs, parent relationships, and timing---enabling post-hoc verification that tool calls, fault injections, and agent responses share a linked trace (\Cref{sec:qualification}).

\paragraph{Failure Classifier.}
The \texttt{FailureClassifier} analyzes completed agent traces and classifies observed failures according to the taxonomy in \Cref{sec:taxonomy}. Classification is rule-based, matching exception types and trace patterns to failure categories. For output consistency (Category~5), the classifier uses token-level Jaccard similarity to detect lexical divergence between paired outputs; this is a surface-level heuristic that can miss semantically significant factual changes (e.g., a city name swap in a long answer) while flagging equivalent paraphrases. The classifier enables automated aggregation of failure statistics across experiment runs but is not used for the main reported metrics.

\subsection{Benchmark Layer}

The benchmark layer provides standardized tasks and metrics for reproducible assessment.

\paragraph{Task Suites.}
Three query groups exercise different prompt complexity levels. All groups are dispatched through the same agent pipeline (tool-augmented single invocation for LangGraph/LangChain; UserProxy--AssistantAgent conversation for AutoGen); the groups differ only in query content:

\begin{itemize}
  \item \textbf{Tool Use} (5 queries): factual lookups and calculations that benefit from web search and calculator tool calls.
  \item \textbf{RAG-Style} (5 queries): knowledge-intensive questions about agent reliability topics, designed to elicit retrieval tool use. (The toolkit defines a \texttt{RAGTask} class with corpus retrieval, but the benchmark runner dispatches these queries through the same tool-augmented agent as other groups; no separate retrieval pipeline is instantiated.)
  \item \textbf{Multi-Agent-Style} (5 queries): open-ended research-and-synthesis prompts that tend to produce longer, multi-step responses. (The toolkit defines a \texttt{MultiAgentTask} with a researcher--analyst pipeline descriptor, but the benchmark runner does not instantiate a multi-agent graph for LangGraph/LangChain; only AutoGen's adapter is inherently multi-agent for all query groups.)
\end{itemize}

\paragraph{Metrics.}
\agentprobe{} computes the following metrics for each experiment condition:

\begin{itemize}
  \item {\color{orange!80!black}\textbf{Initial Exception Rate ($ER$):} Fraction of runs in which the initial \texttt{agent.invoke()} call raised an unhandled exception under injection conditions. This captures all unhandled exceptions, not per-trial causal attribution to injected faults.}
  \item {\color{orange!80!black}\textbf{Keyword Pass Rate ($KW$):} Fraction of runs whose output contains expected keywords for the given query, assessed by the toolkit's \texttt{ResponseGrader}. This is a proxy for task compliance rather than strict factual correctness.}
  \item {\color{orange!80!black}\textbf{Answer-String Presence ($AC$):} For queries with verifiable ground truth, whether the agent's output contains the expected answer substring (e.g., ``paris'' or ``127.05''). This is neither necessary nor sufficient for a correct answer: it can produce false positives (e.g., ``12000 is incorrect'') and false negatives (e.g., a Chinese-language response for Paris). Only 2 of the 5 tool-use queries have unambiguous ground-truth answers; the remaining 3 are open-ended. We report this metric only on the assessable subset.}
  \item \rfour{\textbf{Mean Completion Time ($\bar{T}$):} Average wall-clock time per task.}
  \item {\color{orange!80!black}\textbf{Recovery Rate ($RR$):} Fraction of initial failures from which the agent successfully recovers via a single retry. Undefined (N/A) when no failures occur in a condition.}
\end{itemize}

\noindent The present study reports $ER$, $KW$, $AC$, $\bar{T}$, and $RR$. Additional metrics---token efficiency, failure cascade depth, and cross-run consistency---are defined in the failure taxonomy as desirable measurements but are not yet implemented in the metrics module and are not reported here.

\paragraph{Benchmark Runner.}
The \texttt{BenchmarkRunner} orchestrates experiment execution, managing the lifecycle of injectors, tracers, and task evaluation. It supports configurable parameters including the number of runs per condition, failure injection probability, and framework selection. Per-condition checkpointing ensures that partial results survive process interruptions.

\section{Experimental Methodology}\label{sec:experiments}
% ============================================================================

Our study has two phases. Phase~1 is exploratory: it uncovers an integration-level silent failure. Phase~2 patches that bug and reruns a focused experiment with matched injection probabilities and answer-presence grading. A separate qualification experiment validates the adapter-level pipeline (tool execution, fault injection, trace linkage) using deterministic tasks.

\subsection{Frameworks Under Test}

We evaluate three frameworks with distinct architectural approaches:

\begin{itemize}
  \item \textbf{LangGraph}~\cite{langgraph2024}: A stateful, graph-based orchestration framework where agent behavior is defined as a directed graph of nodes (actions) and edges (transitions). Supports cycles, conditional branching, and persistent state.

  \item \textbf{LangChain}~\cite{langchain2023}: A composable chain-based framework where agent behavior is defined as a sequence of processing steps. Provides high-level abstractions for common patterns (ReAct, tool use).

  \item \textbf{AutoGen}~\cite{wu2023autogen}: A conversational multi-agent framework where agents interact through structured message passing. Supports flexible agent roles and conversation patterns.
\end{itemize}

\subsection{Common Configuration}

Both phases share the following setup:

\begin{itemize}
  \item \textbf{LLM Backend:} Llama~3.1 8B (Q4\_K\_M quantization, Ollama digest prefix \texttt{46e0c10c039e}, identified post-hoc from the same installation) served locally via Ollama~0.31.1. A cross-model validation (\Cref{sec:cross-model}) repeats the qualification and Phase~2 protocol on Mistral~7B (Q4\_K\_M, digest \texttt{6577803aa9a0})~\cite{mistral2024} and Qwen2.5~7B (Q4\_K\_M, digest \texttt{845dbda0ea48})~\cite{qwen25_2024}. Digests were not recorded at experiment time; the historical \texttt{experiment\_metadata.json} files list \texttt{model\_digest:~unknown}. All three models report \texttt{tools} capability in Ollama.
  \item {\color{blue}\textbf{Hardware:} Apple M-series, 16\,GB unified memory, macOS~27. No discrete GPU was present; GPU/Metal offload settings were not recorded at experiment time.}
  \item {\color{blue}\textbf{Framework Versions:} LangGraph~1.2.0, LangChain~1.3.1, langchain-core~1.4.0, pyautogen~0.1.14, openai~0.28.1. The complete installed-version list is recorded in per-batch \texttt{experiment\_metadata.json} files in the repository.}
  \item \textbf{Response Caching:} pyautogen~0.1.14 caches LLM responses via \texttt{diskcache} by default. {\color{orange}Phase~1 did not clear the cache between runs; Phase~2 and all subsequent experiments attempt to clear the cache before each invocation via \texttt{Completion.clear\_cache()}; the adapter silently continues if clearing fails, so cache-free inference is not guaranteed by this mechanism alone. Despite the missing cache-clearing in Phase~1, no millisecond-scale total invocation latencies were observed: all 150 Phase~1 AutoGen runs have latencies between 6.8\,s and 317\,s, with zero sub-5\,s runs. Request-level cache hits within a multi-turn conversation were not recorded.}
  \item \textbf{Random Seed:} 42 for injection sequence control. Ollama does not fix a sampling seed, so repeated runs produce different model outputs.
  \item \textbf{Recovery Procedure:} After a failed run (unhandled exception), the harness immediately retries \texttt{agent.invoke()} once with the same input (\texttt{recovery\_attempts\,=\,1}). No backoff is applied. The fault injector remains active during the retry, so the retry may also encounter an injected fault (with the same per-call probability). A run is marked as \emph{recovered} if the retry completes without exception.
  \item \textbf{Error Detection:} A run is recorded as an \emph{error} if the initial \texttt{agent.invoke()} call raises an unhandled exception. This captures all unhandled exceptions under injection conditions, including any unrelated errors; we therefore report ``initial exception rate under injection conditions'' rather than claiming per-trial causal attribution to injected faults.
\end{itemize}

\subsection{Phase 1: Exploratory Experiment}\label{sec:phase1-method}

Phase~1 evaluates all three query groups across all three frameworks:

\begin{itemize}
  \item \textbf{Runs per Condition:} 30 for LangGraph and LangChain; 10 for AutoGen (constrained by its multi-turn protocol overhead, which makes each run approximately 11$\times$ slower on average: mean first-attempt latency 84.9\,s for AutoGen vs 7.5--7.7\,s for LangGraph/LangChain across all 1{,}050 Phase~1 trials). Each run cycles through 5 queries per task type via round-robin assignment.
  \item \textbf{Failure Injection Probability:} $p = 0.20$ for timeout and malformed output; $p = 0.15$ for rate limit and API error.
  \item \textbf{Query Groups:} All three---tool use (5 queries), RAG-style (5 queries), multi-agent-style (5 queries)---for 15 queries total.
  \item \textbf{Conditions:} $3~\text{frameworks} \times 3~\text{task types} \times 5~\text{fault conditions} = 45$ conditions (15 per framework), yielding $(15 \times 30) + (15 \times 30) + (15 \times 10) = 1{,}050$ total runs (LangGraph + LangChain at $n = 30$, AutoGen at $n = 10$).
  \item \textbf{Correctness Grading:} Not active; only error rate and recovery are measured.
\end{itemize}

\subsection{Phase 2: Patched Validation Experiment}\label{sec:phase2-method}

{\color{magenta}Phase~1 trace analysis revealed that AutoGen never invoked tools (\Cref{sec:phase1-results}). We implemented a compatibility patch (\texttt{\_patch\_openai\_compat()}) that translates between pyautogen's legacy \texttt{functions} parameter and Ollama's \texttt{tools} parameter, and converts \texttt{tool\_calls} responses back to \texttt{function\_call} format for pyautogen's execution loop. Phase~2 reruns the experiment with this patch applied:}

\begin{itemize}
  \item \textbf{Runs per Condition:} 30 for all three frameworks (symmetric).
  \item \textbf{Failure Injection Probability:} $p = 0.20$ for all four fault types (matched, addressing the Phase~1 confound).
  \item \textbf{Query Group:} Tool use only (5 queries). We restrict to tool-use tasks to isolate the effect of the patched tool-calling path; RAG-style and multi-agent-style queries remain untested in Phase~2.
  \item \textbf{Conditions:} $3~\text{frameworks} \times 1~\text{task type} \times 5~\text{fault conditions} = 15$ conditions, yielding $15 \times 30 = 450$ total runs.
  \item \textbf{Correctness Grading:} Active. The \texttt{ResponseGrader} checks keyword compliance; answer-string presence is adjudicated post-hoc by checking whether the saved output contains the expected ground-truth substring, on the two assessable queries (indices~0 and~2 in the tool-use suite: ``What is the capital of France?'' and ``Calculate 15\% of 847''). Correct-answer presence does not prove required tool use.
  \item \textbf{Timeout Budget:} The benchmark harness enforces a 120-second wall-clock timeout per invocation. Timeout injection imposes a 5-second \texttt{time.sleep} before raising; the other three fault types raise immediately. pyautogen's per-request timeout (\texttt{Completion.request\_timeout}) remains at its default 60~seconds.
\end{itemize}

\subsection{Qualification Experiment}\label{sec:qualification-method}

{\color{magenta}To validate the adapter-level pipeline---tool execution, fault injection, answer-string presence, and trace linkage---we run a small qualification experiment with deterministic tasks (this validates the injector and agent adapters but not runner-level timeout or retry behavior):}

\begin{itemize}
  \item \textbf{Tasks:} Two calculator queries with known ground truth: ``Compute $7919 \times 6841$'' (expected: 54{,}173{,}879) and ``Compute $3571 + 8429$'' (expected: 12{,}000). The explicit tool-call event is the evidence of tool execution, not the arithmetic difficulty of the query.
  \item \textbf{Phases:} (a)~Baseline ($p = 0$): verifies, on the same log record, that the required tool was called by registered name, that the call arguments contain the complete expected expression (e.g., \texttt{3571 + 8429}, not merely an operand fragment), that the tool's return value equals the expected answer, and that the final output contains the answer. (b)~Guaranteed fault ($p = 1.0$, API error 503): verifies that a fault was injected at the required tool boundary.
  \item \textbf{Tracing:} OpenTelemetry \texttt{InMemorySpanExporter} captures all spans, which are serialized to JSON with trace IDs, span IDs, and parent relationships.
  \item \textbf{Trials:} $3~\text{frameworks} \times 2~\text{tasks} \times 2~\text{phases} = 12$ trials.
\end{itemize}

\subsection{Experimental Conditions}

We define the following experimental conditions for each framework:

\begin{enumerate}
  \item \textbf{Baseline} ($C_0$): No fault injection. Establishes the framework's performance under ideal conditions.
  \item \textbf{Timeout Injection} ($C_1$): Tool calls may time out with probability $p$.
  \item \textbf{Malformed Output Injection} ($C_2$): Tool calls may raise a \texttt{ValueError} exception with probability $p$ (simulating a malformed upstream response; see \Cref{sec:discussion} for scope).
  \item \textbf{Rate Limit Injection} ($C_3$): Tool calls may return rate limit errors with probability $p$.
  \item \textbf{API Error Injection} ($C_4$): Tool calls may return generic API errors with probability $p$.
\end{enumerate}

\subsection{Statistical Analysis}

We report Wilson score 95\% confidence intervals for proportions (error rate, recovery rate). Each CI is computed on the per-condition denominator (e.g., $n = 30$ trials for error rate, $n = k$ failures for recovery rate where $k$ is the observed failure count); we do not pool across fault types because the four conditions share the same seed and produce identical failure sets within each model. Recovery rate is reported as undefined (N/A) when no failures occur in a condition, rather than as 0\%.

{\color{orange}\textbf{Dependence across conditions.} Because the four injection conditions ($C_1$--$C_4$) share seed~42 and LangGraph/LangChain share the same underlying execution path (\Cref{sec:lg-lc-convergence}), the eight LangGraph/LangChain injection cells in \Cref{tab:phase2-error} exhibit identical failure and recovery counts (7/30 failures, 5/7 recoveries). The shared seed means these cells reflect one failure/recovery pattern, not eight independent replications. Individual runs still differ in model output, latency, and answer content (the 450 executions are real), but the fault-injection trigger sequence and exception-propagation path are common across conditions. We retain the per-condition breakdown for transparency but caution against interpreting the uniform counts as independent evidence.}

\subsection{Phase 1: Integration Bug Discovery}\label{sec:phase1-results}

Phase~1 completed 1{,}050 runs across 45 conditions. Full data are in the project repository; the key findings follow.

\paragraph{LangGraph and LangChain.} Under fault injection, both frameworks exhibit an initial exception rate of 16.1\% [95\%~Wilson~CI: 12.7--20.3\%] across 360 injection runs each, with 83\% overall recovery. These two frameworks produce identical failure counts, because LangChain~1.3 delegates agent execution to LangGraph internally. Source inspection confirms that both wrappers use the same underlying execution path; the identical counts are consistent with shared code rather than coincidental equivalence.

\paragraph{AutoGen: Silent tool bypass.} AutoGen shows a 5.8\% error rate under injection [95\%~CI: 2.9--11.6\%, $n = 120$], but trace analysis reveals that the LLM never invokes tools. pyautogen~0.1.14 sends tool definitions using the legacy \texttt{functions} parameter, which Ollama's OpenAI-compatible endpoint silently ignores. Llama~3.1 never receives the formatting cue it needs to emit a tool-call JSON block, so it answers every query from parametric knowledge alone and the fault injectors are never triggered. This is an ecosystem integration bug---a mismatch between the client library's API schema and the inference server's supported parameters. Ollama issue~\#3927 reports related silent parameter-dropping behavior, though we have not confirmed the exact internal code path.\footnote{See \url{https://github.com/ollama/ollama/issues/3927}. AutoGen issue~\#4225 (\url{https://github.com/microsoft/autogen/issues/4225}) reports a related dependency failure but does not document the exact silent-schema mismatch observed here.} AutoGen's errors are entirely conversation-protocol timeouts from pyautogen's 60-second per-request limit, unrelated to injected faults.

\paragraph{Motivation for Phase~2.} Phase~1 AutoGen results are uninterpretable for fault-tolerance comparison because the injected faults never fire. The asymmetric probabilities ($p = 0.15$ vs $p = 0.20$) also confound fault-type comparisons, and answer-presence grading was not active. Phase~2 fixes all three issues.

\rthree{Three findings generalize across all tested models:}

\begin{enumerate}
  \item {\color{green!50!black}\textbf{Seed-fixed injection.} The fixed seed produces a deterministic injection sequence, but the number of tool calls and injections encountered per condition varies by model: Llama~3.1 makes 37~calls and encounters 9~injections per LG/LC condition, while Mistral and Qwen2.5 make 53--54~calls and encounter 12~injections. Whether this error absorption is inherent to the conversation protocol, specific to the adapter version, or influenced by model size remains an open question (see \Cref{sec:discussion}).}
\end{enumerate}

{\color{green!50!black}Recovery rates differ across models---Llama~3.1: 5/7 (71.4\%), Mistral: 5/8 (62.5\%), Qwen2.5: 4/8 (50.0\%)---but these are small-sample counts with widely overlapping confidence intervals, and the models encounter different numbers of injections (9 vs 12) due to different tool-call patterns. We do not attribute the differences to specific model capabilities. The initial answer-string-presence gap (Qwen2.5 83.3\% vs 75.0\% for Llama/Mistral) has a direct explanation: Qwen2.5 loses two assessable trials per injection condition while the other models lose three, reflecting different placement of failures rather than alternative reasoning. After the allowed retry, all three models reach 44/48 (91.7\%) assessable-answer presence on LG/LC injection conditions, eliminating the apparent initial-answer advantage.}

{\color{green!50!black}The framework-level observations are consistent across the tested configurations: LangGraph/LangChain propagate exceptions to the harness (which retries once with reinjection active) across all three models, while AutoGen absorbs exceptions internally in the two completed injection configurations (Llama~3.1 and Qwen2.5; Mistral AutoGen injection was not attempted). This consistency strengthens the finding but does not establish it as a universal architectural property, since all configurations share the same backend, adapter code, and protocol shim.}

\section{Discussion}\label{sec:discussion}
% ============================================================================

\subsection{Why LangGraph and LangChain Converged}\label{sec:lg-lc-convergence}

{\color{orange!80!black}The identical failure counts across both phases are consistent with source-code inspection showing that LangChain~1.3 delegates tool dispatch to LangGraph under the hood: both frameworks share the same underlying \texttt{ToolNode} and execution path at the tool-calling boundary. The identical counts extend to recovery outcomes because the fixed seed produces the same injection sequence, and the common benchmark harness applies one retry with reinjection active---the same external procedure for both wrappers. A more informative comparison would have used a pre-LangGraph version of LangChain (the now-deprecated \texttt{AgentExecutor}) against LangGraph. This highlights a broader lesson for benchmarking: framework APIs can be misleading proxies for architectural difference.}

\subsection{AutoGen's Error-Absorption Behavior}

Phase~1 revealed that AutoGen never called tools (an integration bug). Phase~2, with the compatibility patch applied, reveals a more nuanced picture: AutoGen \emph{does} call tools, faults \emph{are} injected (15 recorded injections per condition under the fixed seed), but the adapter returns tool exceptions as function-response messages to the AssistantAgent, which continues the conversation---either retrying the tool call or answering from parametric knowledge. This produces a 0\% unhandled-exception rate but does not mean the agent handled the fault correctly: it often produces incorrect answers. The 0\% exception rate is substantially explained by pyautogen~0.1.14's \texttt{execute\_function()} implementation, which catches exceptions raised by tool functions and converts them to \texttt{(False, "Error:~...")} response tuples. This is a library exception-to-message policy, not an agent-level recovery mechanism; it measures exception propagation rather than task resilience.

The practical implication is worrying: in production, agents with this policy silently degrade rather than fail loudly, potentially returning plausible but wrong answers. The 33.3\% baseline answer-string presence on assessable questions (vs 100\% for LangGraph/LangChain, $n = 12$ each; this Llama~3.1 figure uses the historical answer extractor and has not been rerun with the corrected version---see \Cref{sec:limitations}) suggests that even without faults, the pyautogen~0.1.14 adapter with local Llama~3.1 inference produces unreliable outputs. Cross-model validation (\Cref{sec:cross-model-phase2}) shows this pattern holds across the tested configurations: Qwen2.5 achieves 0\% (0/12) AutoGen baseline answer-string presence; one baseline response correctly identifies Paris in Chinese but fails the English-substring check, so the 0\% figure reflects the string-matching metric, not necessarily zero factual knowledge.

\paragraph{Traced diagnostic: direct client vs AutoGen shim.}
{\color{green!50!black}To investigate whether AutoGen's low answer-string presence is caused by the model, the protocol conversion, or the adapter's continuation policy, we ran a diagnostic comparing two execution paths on the same three deterministic tasks:
(1)~a \emph{direct client} calling Ollama's \texttt{/v1/chat/completions} endpoint with the native \texttt{tools}/\texttt{tool\_calls} format (using the same openai~0.28.1 library), and
(2)~the full \emph{AutoGen shim} (pyautogen~0.1.14 with \texttt{\_patch\_openai\_compat()}).
Both paths used identical tool schemas, system prompts, model weights, and temperature ($T = 0$). All direct-client tasks ran first in an unpatched process to prevent contamination from the AutoGen compatibility shim.}

\Cref{tab:diagnostic} summarizes the results.
Through the direct client (run before any AutoGen code to prevent patch contamination), both Llama~3.1 and Qwen2.5 call each tool exactly once, receive the correct result, and produce a text answer containing the expected value---achieving 2/3 literal answer-string presence (the multiplication answer \texttt{54,173,879} is numerically correct but the comma-formatted output does not match the unformatted expected string \texttt{54173879}; all three answers are factually correct under comma-normalized matching).
Through the AutoGen shim (also $T = 0$), the same models diverge: Llama~3.1 calls tools 3 times per task. On the France query, the expected substring appears in AutoGen's selected final message after repeated calls. On the other two, the model hallucinates a different number (e.g., the calculator returns \texttt{54173879} but the model's final message reports 54{,}444{,}919). Qwen2.5 calls tools 4--5 times per task; on the France query, the selected final message contains non-answer text (a raw JSON tool description) rather than a factual response, while the arithmetic tasks end with empty selected text and a pending tool call at the turn limit.

\subsection{Error Rate Is Not Enough}

AutoGen's 0\% error rate alongside 33.3\% baseline answer-string presence (historical extractor) is a cautionary example: an agent that absorbs every exception looks resilient by error-rate measures but may be returning empty or incorrect answers. LangGraph/LangChain's 23.3\% error rate under injection sounds alarming by comparison, but on baseline assessable questions (no injection), answer-string presence is 100\% [95\%~Wilson~CI: 75.8--100\%, $n = 12$]. Under injection, initial answer-string presence is 75.0\% (36/48 assessable trials) for LangGraph/LangChain and 39.6\% (19/48) for AutoGen. A composite metric combining survival, correctness, and trace evidence---as demonstrated in the qualification experiment---provides a more complete picture.

\subsection{Uniform Recovery Across Fault Types}

In Phase~2, all four fault types produce identical error rates (23.3\%) and recovery rates (71.4\%) for LangGraph/LangChain. This contrasts with Phase~1, where rate-limit/API-error recovery (93\%) appeared higher than timeout/malformed-output recovery (73\%). The Phase~1 gap was confounded with injection probability ($p = 0.15$ vs $p = 0.20$); Phase~2's matched $p = 0.20$ eliminates this confound. All four sub-types raise exceptions at the tool-call boundary, and the exception content does not reach the LLM. Timeout injection additionally imposes a 5-second \texttt{time.sleep} delay before raising; the other three types raise immediately. Despite this timing difference, the same error and recovery counts were observed for all four types under this particular seed and schedule. This does not establish that timing has no independent effect in general---only that it did not produce a measurable difference in this configuration. Differentiating fault-type effects would require larger sample sizes and multiple seeds, as well as injection mechanisms with genuinely distinct failure signatures (e.g., corrupted data that reaches the model's context).

\subsection{Scope of ``Malformed Output'' Injection}

{\color{orange!80!black}The current ``malformed output'' injector raises an exception rather than returning corrupted data to the agent. This means it tests the agent's exception-handling path, not its ability to parse or reason about damaged tool responses. A true malformed-output test would return syntactically valid but semantically incorrect data (e.g., a JSON response with wrong field values) and check whether the agent detects the inconsistency. This is an important direction for future work that would exercise a different failure surface.}

\subsection{Implications for Hybrid Architectures}

The failure modes we catalogued map onto the classical symbolic/sub-symbolic divide. Orchestration errors (infinite loops, wrong branches) are the kind of problem that BDI-style goal management was designed to address, and context degradation would in principle be less dangerous when state lives in a logical database rather than an LLM's attention window---though our experiments do not test these hypotheses directly.

LLM-based agents win on flexibility---they handle ambiguous natural-language queries and use tools they were not explicitly programmed for. A hybrid architecture might use a BDI planner for high-level goals and tool-invocation requirements (potentially preventing AutoGen-style silent error absorption) while delegating individual tool calls and language reasoning to the LLM. Recent work on self-healing agentic orchestrators~\cite{sureshbabu2026selfhealing} explores automated recovery strategies for tool-augmented LLM systems, which could complement such hybrid designs. Whether such a design actually mitigates the failures observed here is an empirical question; \agentprobe{}'s fault injectors could serve as a regression suite for evaluating it.

\subsection{Limitations}\label{sec:limitations}

\begin{itemize}
  \item {\color{magenta}\textbf{Local open-weight models only.} The main study uses Llama~3.1 8B via Ollama, with cross-model validation on Mistral~7B and Qwen2.5~7B (\Cref{sec:cross-model}). All three are 7--9B parameter quantized models on a single local backend. Larger models or cloud-hosted APIs with constrained decoding may produce different results, particularly for AutoGen's answer-string presence.}
  \item {\color{magenta}\textbf{Single seed.} Both phases use seed~42 for injection control. While this ensures reproducibility, it means the specific set of injected trials is fixed. Different seeds would produce different injection sequences and potentially different failure/recovery counts; the Wilson CIs quantify sampling uncertainty conditional on this design, not a guarantee that future seeds will fall within these bounds.}
  \item {\color{magenta}\textbf{Tool-use only in Phase~2.} RAG-style and multi-agent-style queries were not rerun after patching AutoGen. Whether AutoGen's error-absorption behavior extends to more complex query types is unknown.}
  \item {\color{magenta}\textbf{Taxonomy--evaluation gap.} The taxonomy defines five failure categories, but experiments inject only tool-call faults. Orchestration and context injectors are implemented but not experimentally validated.}
  \item {\color{magenta}\textbf{Malformed-output scope.} The ``malformed output'' injector raises exceptions rather than returning corrupted data, making it functionally equivalent to the other fault types in the current implementation.}
  \item {\color{magenta}\textbf{Answer-string presence on 40\% of queries.} Only 2 of 5 tool-use queries have verifiable ground truth. Answer-presence claims are scoped to this assessable subset; the remaining 60\% are evaluated only by keyword presence, which is a weak proxy.}
  \item {\color{magenta}\textbf{LangChain--LangGraph convergence.} This is version-specific to LangChain~1.3; earlier versions using the deprecated \texttt{AgentExecutor} may behave differently.}
  \item {\color{magenta}\textbf{AutoGen version.} The tool-calling patch and error-absorption behavior are specific to pyautogen~0.1.14; the community fork (AG2) and Microsoft's AutoGen~0.4 rewrite may handle faults differently.}
  \item {\color{magenta}\textbf{Unmatched injection exposure.} Although the same random seed is used, models encounter different numbers of tool calls and injections per condition (e.g., 37~calls/9~injections for Llama vs 53--54~calls/12~injections for Mistral/Qwen). Cross-model recovery comparisons are therefore descriptive rather than controlled.}
  \item {\color{magenta}\textbf{Incomplete Mistral AutoGen.} Mistral's AutoGen baseline completed only 5 of 30 planned runs before persistent timeouts; its four injection conditions were not attempted. Mistral AutoGen results are an aborted configuration, not a completed comparison.}
  \item {\color{magenta}\textbf{Shared adapter and backend.} All three models use the same Ollama backend, protocol shim, and adapter code. Cross-model consistency demonstrates robustness within this stack but does not isolate framework architecture from adapter implementation.}
  \item {\color{magenta}\textbf{AutoGen output extraction and mixed adapter versions.} The AutoGen adapter extracts the last non-empty assistant message from the conversation history. In pyautogen~0.1.14, tool-call messages have role \texttt{assistant} with empty content; the corrected extractor skips these and returns the last substantive response. However, only Qwen2.5's AutoGen cells have been rerun with the corrected extractor (batch \texttt{20261112\_063451}); Llama~3.1 and Mistral AutoGen results use the historical extractor. The two configurations are labeled in \Cref{tab:cross-model-phase2}. Qwen2.5's rerun baseline produces 0\% answer-string presence (0/12) vs the historical batch's 8.3\% (1/12); this difference involves both the extraction change and different inference trajectories, so neither factor can be isolated. Despite the corrected extractor, 70\% of Qwen AutoGen baseline responses remain empty. Qwen2.5's injection answer-string presence (6/48, 12.5\%) exceeds its baseline (0/12); this counterintuitive inversion likely reflects small-sample variability rather than injection improving outputs, since both rates are low and their Wilson CIs overlap substantially. The traced diagnostic (\Cref{tab:diagnostic}) shows that both models produce correct answers when the AutoGen adapter is bypassed, pointing to the adapter layer as a likely source, though the diagnostic confounds message format with stopping policy and answer selection (temperature is matched at $T\!=\!0$).}
\end{itemize}

\subsection{Threats to Validity}

\paragraph{Internal Validity.} {\color{magenta}The use of controlled fault injection with fixed probability and seed ensures reproducibility but limits generalizability. With 30 runs per condition, each of the 5 queries repeats 6 times via round-robin, so runs using the same query are not fully independent. We report Wilson score confidence intervals throughout. The matched injection probability in Phase~2 eliminates the Phase~1 confound between fault type and injection rate.}

\paragraph{External Validity.} {\color{magenta}The main study uses Llama~3.1 8B on Ollama, with cross-model validation on Mistral~7B and Qwen2.5~7B (\Cref{sec:cross-model}). All three are locally hosted 7--9B quantized open-weight models on a single backend, without constrained decoding or server-side JSON enforcement. Cloud-hosted frontier APIs (GPT-4o, Claude) typically provide structured-output enforcement, which may substantially change tool-calling reliability. The cross-model validation shows that error propagation in LangGraph/LangChain is consistent across all three model architectures on this backend; AutoGen error absorption is confirmed for the two completed injection configurations (Llama~3.1 and Qwen2.5; Mistral AutoGen injection was not attempted after baseline instability). This does not establish generality beyond these configurations. The specific failure modes and answer-presence gaps vary with model. Extension to larger models and cloud-hosted backends remains the highest-priority future work (see item~1 in Future Work).}

\paragraph{Construct Validity.} {\color{magenta}We measure three complementary dimensions: error rate (survival), keyword pass rate (compliance), and answer-string presence (whether the expected answer substring appears in the output). The qualification experiment validates the adapter-level pipeline (tool execution, fault injection, and trace linkage) with linked traces but does not cover runner-level timeout or retry behavior. However, the 60\% of queries without verifiable ground truth limits the scope of answer-presence claims. Zhu et~al.~\cite{zhu2025benchmarking} provide best-practice guidelines for building rigorous agentic benchmarks; our design aligns with several of their recommendations (controlled conditions, reproducible seeds) but falls short on others (limited task diversity, single seed). Future work should use tasks with 100\% assessable ground truth.}


% ============================================================================
\section{Conclusions and Future Work}\label{sec:conclusion}
% ============================================================================

The central lesson of this work is that a single reliability metric can be profoundly misleading. In Phase~1, AutoGen exhibited a lower error rate than LangGraph/LangChain under fault injection---not because it handled faults better, but because an API-schema mismatch silently prevented tool execution. In Phase~2, after patching the integration bug, AutoGen achieved a 0\% error rate while tools were verifiably called and faults were verifiably injected---but the expected answer string appeared in only 4 of 12 assessable baseline trials (33\%; historical extractor---Qwen2.5's rerun with the corrected extractor gives 0\%). LangGraph/LangChain, by contrast, failed loudly 23.3\% of the time under injection but achieved 12/12 answer-string presence on baseline assessable questions (100\%). Under injection, initial answer-string presence was 75\% (36/48) for LangGraph/LangChain and 39.6\% (19/48) for AutoGen. Without trace-level observability and answer-presence grading, either phase's results could have been misinterpreted. A traced diagnostic (\Cref{tab:diagnostic}) showed that when the AutoGen shim is bypassed and the same models call tools through the native \texttt{tools}/\texttt{tool\_calls} format, both Llama~3.1 and Qwen2.5 produce factually correct answers on all three deterministic tasks (3/3 under comma-normalized matching; 2/3 under the literal-substring rule used elsewhere), while the AutoGen shim produces 1/3 (Llama) and 0/3 (Qwen)---suggesting the adapter/protocol layer plays a substantial role, though the compared paths still differ in stopping policy and answer selection. Cross-model validation on Mistral~7B and Qwen2.5~7B (\Cref{sec:cross-model}) shows that LangGraph/LangChain error propagation is consistent across all three 7--9B models on the same backend, while AutoGen error absorption is confirmed for the two completed injection configurations (Llama~3.1 and Qwen2.5; Mistral AutoGen injection was not attempted). Recovery rates and failure placement vary by model. After the allowed retry, all three models reach the same assessable-answer rate (91.7\%) for LG/LC, suggesting that initial-answer differences reflect fault placement rather than model capability.

The toolkit, taxonomy, full experimental data, and qualification artifacts are available at \url{https://github.com/chhayankjain/AgentProbe}. We encourage other groups to run \agentprobe{} on their own framework and model combinations and to contribute injector modules for failure modes we have not yet covered.

\paragraph{Future Work.}
The most pressing next steps are:

\begin{enumerate}
  \item {\color{green!50!black}\textbf{Larger models and cloud backends.} Our cross-model validation (\Cref{sec:cross-model}) covers three 7--9B quantized models on a single local backend but does not include larger models (Llama~3.1 70B, GPT-4o, Claude), different serving stacks (vLLM, TGI), or cloud-hosted APIs with native function-calling and constrained decoding. The traced diagnostic (\Cref{tab:diagnostic}) points to the adapter/protocol layer as a likely factor in AutoGen's answer-presence gap, but confounds message format with stopping policy and answer selection (temperature is matched at $T\!=\!0$). A configuration with native tool-calling support and controlled factor isolation would establish which specific differences cause the gap.}

  \item {\color{orange!80!black}\textbf{Full-spectrum assessable tasks.} The current tool-use suite has only 40\% assessable questions. Future experiments should use tasks where every query has unambiguous ground truth, enabling answer-presence measurement on the full population.}

  \item {\color{orange!80!black}\textbf{Additional taxonomy categories.} Experimentally validating the orchestration-error and context-degradation injectors is a high priority. The current results cover only tool-call faults.}

  \item {\color{blue}\textbf{Realistic fault models.} Our injection is uniform and independent; production failures tend to be bursty and correlated. Under correlated faults, a failure during the first attempt would persist into the retry, likely reducing recovery rates below those observed with independent per-call injection. A correlated-failure injector would bring \agentprobe{}'s fault model closer to production reality.}

  \item {\color{orange!80!black}\textbf{True malformed-output injection.} Two distinct directions remain: schema/format errors (e.g., truncated JSON, wrong field types) and semantic corruption (syntactically valid but factually incorrect data). Both would test agents' ability to detect and handle corrupted tool responses---a distinct failure surface from the exception path tested here.}

  \item {\color{magenta}\textbf{Multiple seeds.} Validating results across multiple injection seeds would strengthen the statistical claims beyond the single seed~42 used here.}
\end{enumerate}
