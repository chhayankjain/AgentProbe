\abstract{
LLM-based intelligent agents are increasingly deployed in production systems, yet how they behave under adverse conditions is not well understood. We present AgentProbe, an open-source fault-injection and observability toolkit for systematically evaluating agent resilience. AgentProbe implements a five-category failure taxonomy---tool call faults, orchestration errors, context degradation, latency anomalies, and output consistency violations---with configurable injectors, OpenTelemetry-based tracing, and 15 benchmark queries (5 per task type) spanning tool use, retrieval-augmented generation, and multi-agent coordination.
%
We evaluate the tool-call fault category by comparing three agent frameworks---LangGraph, LangChain, and AutoGen---across 1{,}050 experiment runs (3 frameworks $\times$ 3 task types $\times$ 5 fault conditions $\times$ 10--30 runs) using Llama~3.1 8B via Ollama. Under fault injection, LangGraph and LangChain exhibit a 16.1\% fault-triggered error rate [95\% CI: 12.7--20.3\%] with 79\% recovery. AutoGen's overall error rate is 8.0\% [4.6--13.5\%], but trace analysis reveals its failures are entirely unrelated to the injected faults: the LLM never invokes tools due to a legacy API-parameter mismatch silently ignored by Ollama, so injected faults never trigger. AutoGen's failures instead stem from conversation-protocol timeouts in multi-agent tasks, producing a 16.7\% baseline error rate versus 0\% for the other two frameworks. LangGraph and LangChain show no significant difference ($p = 1.0$), recovering more effectively from rate-limit and API errors (86\%) than from timeouts and malformed outputs (73\%). Taken together, these results show that conventional pass/fail metrics can hide serious architectural weaknesses, making systematic fault injection and trace-level observability a necessity for meaningful agent evaluation.
}

\section{Introduction}\label{sec:introduction}
% ============================================================================

The concept of intelligent agents---autonomous software entities that perceive their environment and act upon it to achieve delegated goals---has been a central thread in artificial intelligence research since at least the 1950s~\cite{wooldridge2009introduction}. The agent-oriented paradigm, consolidated in the mid-1990s after two periods of reduced AI research activity, established a rigorous framework in which agents are characterized by autonomy, reactivity, proactivity, and social ability~\cite{wooldridge1995intelligent}. The Beliefs--Desires--Intentions (BDI) architecture emerged as a dominant model for rational decision-making, grounding agent behavior in a formalism derived from practical reasoning~\cite{rao1995bdi}.

A new generation of intelligent agents has emerged with the advent of Large Language Models (LLMs). These \emph{AI agents} employ LLMs as reasoning engines, using architectures such as ReAct~\cite{yao2023react} and Chain of Thought (CoT)~\cite{wei2022chain} prompting to interleave reasoning with action execution. Unlike their symbolic BDI predecessors, these sub-symbolic agents derive their capabilities from statistical patterns learned during pre-training, gaining flexibility at the cost of introducing new failure modes with no formal characterization.

The deployment of LLM-based agents in production systems has accelerated rapidly. Agent-oriented frameworks such as LangGraph~\cite{langgraph2024}, LangChain~\cite{langchain2023}, and AutoGen~\cite{wu2023autogen} enable developers to build sophisticated multi-agent systems that coordinate tool use, retrieval-augmented generation (RAG), and inter-agent communication. However, little is known about how reliable these systems are when things go wrong. Production incident reports point to recurring failure patterns: API timeouts that cascade through agent loops, context window overflow that triggers hallucinated histories, and orchestration deadlocks in multi-agent handoffs. Yet no systematic methodology exists for reproducing, measuring, or comparing these failure modes across frameworks.

We address this gap with three contributions:

\begin{enumerate}
  \item \textbf{A failure taxonomy for LLM-based agents.} We propose a five-category classification of failure modes observed in production agent systems: tool call faults, orchestration errors, context degradation, latency anomalies, and output consistency violations (\Cref{sec:taxonomy}).

  \item \textbf{The \agentprobe{} toolkit.} We present an open-source Python toolkit that provides configurable fault injectors for four injectable categories (consistency violations are detected, not injected), an observability layer built on OpenTelemetry~\cite{opentelemetry2024} for distributed tracing and metrics collection, and standardized benchmark tasks for reproducible evaluation (\Cref{sec:system}).

  \item \textbf{A comparative empirical study.} We apply \agentprobe{} to evaluate three prominent agent-oriented frameworks---LangGraph, LangChain, and AutoGen---under controlled fault injection, revealing significant architectural differences in resilience and recovery behavior (\Cref{sec:experiments,sec:results}).
\end{enumerate}

The remainder of this paper is organized as follows. \Cref{sec:related} reviews related work on agent reliability, fault injection, and LLM evaluation. \Cref{sec:taxonomy} presents our failure taxonomy. \Cref{sec:system} describes the \agentprobe{} system architecture. \Cref{sec:experiments} details our experimental methodology. \Cref{sec:results} presents and analyzes results. \Cref{sec:discussion} discusses implications for agent-oriented system design. \Cref{sec:conclusion} concludes with future directions.

\section{Related Work}\label{sec:related}
% ============================================================================

\subsection{Agent-Oriented Architectures: From BDI to LLM Agents}

The BDI model, formalized by Rao and Georgeff~\cite{rao1995bdi}, provides a theoretical foundation for rational agency based on mental attitudes. Implementations such as Jason~\cite{bordini2007programming} and JACK~\cite{winikoff2005jack} demonstrated the viability of symbolic agent architectures in multi-agent systems. These systems benefit from formal verification properties but struggle with the flexibility required for open-domain environments.

LLM-based agents mark a shift from symbolic to sub-symbolic reasoning. The ReAct framework~\cite{yao2023react} demonstrated that LLMs can interleave reasoning traces with action execution, while Chain of Thought prompting~\cite{wei2022chain} showed that explicit reasoning steps improve task performance. Modern agent frameworks operationalize these ideas: LangGraph provides a stateful graph-based orchestration model, LangChain offers a composable chain abstraction, and AutoGen enables conversational multi-agent coordination~\cite{wu2023autogen}.

Despite their flexibility, LLM-based agents lack the formal guarantees that BDI architectures provide. Several authors have argued for integrating symbolic and sub-symbolic approaches to combine the strengths of both paradigms~\cite{wooldridge2009introduction}. Our experiments show concretely where sub-symbolic agents fail, which should be useful when designing such hybrid systems.

\subsection{Reliability and Fault Injection}

Fault injection has a long history in distributed systems research, from early work on hardware fault simulation~\cite{hsueh1997fault} to modern chaos engineering practices popularized by Netflix's Chaos Monkey~\cite{basiri2016chaos}. In the software domain, tools such as Chaos Toolkit~\cite{chaostoolkit2024} and Gremlin provide programmable fault injection for microservices architectures.

The application of fault injection to AI systems is comparatively nascent. Existing work has focused on adversarial robustness of neural networks~\cite{goodfellow2015explaining} and test-time perturbations for model evaluation~\cite{ribeiro2020beyond}. However, fault injection at the \emph{system level}---targeting the tools, orchestration logic, and infrastructure that surround the LLM---has received limited attention. \agentprobe{} fills this gap by providing fault injectors that operate at the agent-system boundary rather than at the model level. ToolEmu~\cite{ruan2024toolemu} takes a complementary approach, using an LLM to emulate tool execution in a sandbox so that agent safety risks can be evaluated at scale without real tool infrastructure; however, it targets safety evaluation rather than resilience under infrastructure faults.

\subsection{LLM Evaluation and Benchmarking}

Benchmarks for LLM capabilities have proliferated, including MMLU~\cite{hendrycks2021measuring}, HumanEval~\cite{chen2021evaluating}, and AgentBench~\cite{liu2023agentbench}. These focus primarily on task correctness under ideal conditions. More recent agent benchmarks like $\tau$-bench~\cite{yao2024tau} and WebArena~\cite{zhou2024webarena} use realistic environments, but to our knowledge none of them inject faults systematically to test resilience.

Concurrently, Cemri et~al.~\cite{cemri2025mast} introduce MAST, an empirically grounded taxonomy of 14 multi-agent failure modes derived from 1{,}600+ annotated traces across seven MAS frameworks. Their taxonomy emphasizes inter-agent coordination failures, complementing our taxonomy's focus on tool-call and infrastructure faults.

Observability for LLM systems has been addressed by tools such as LangSmith, Weights \& Biases, and OpenLLMetry~\cite{openllmetry2024}, which provide tracing and logging. What sets \agentprobe{} apart is that it couples observability with controlled fault injection, so failures can be traced to their cause rather than merely logged. In summary, existing agent benchmarks evaluate task correctness under ideal conditions, ToolEmu sandboxes tool execution for safety analysis, and MAST categorizes coordination failures from post-hoc traces. None of these inject infrastructure-level faults into \emph{live} framework executions and capture the resulting failure cascades through distributed tracing. \agentprobe{} occupies this niche: it is, to our knowledge, the first open-source toolkit that combines runtime fault injection with OpenTelemetry-based observability for comparative resilience testing of LLM agent frameworks.

\section{Failure Taxonomy}\label{sec:taxonomy}
% ============================================================================

We propose a five-category failure taxonomy for LLM-based intelligent agents, derived from analysis of production incident reports, framework documentation, and community discussions. Each category captures a distinct failure surface in the agent-system architecture.

\subsection{Tool Call Faults}

Tool call faults occur at the boundary between the agent and external services or APIs. These are the most common failure mode in production agent systems, as agents typically rely on multiple external tools (search engines, databases, code executors) that may fail independently.

\begin{itemize}
  \item \textbf{API Timeout:} The external service does not respond within the expected time window, causing the agent to block or retry indefinitely.
  \item \textbf{Malformed Output:} The tool returns a response that does not conform to the expected schema, causing parsing failures or incorrect downstream reasoning.
  \item \textbf{Rate Limit:} The external service throttles requests, forcing the agent to handle backpressure or degrade functionality.
  \item \textbf{API Error:} The service returns an error response (e.g., HTTP 5xx), requiring the agent to decide between retry, fallback, or graceful termination.
\end{itemize}

\subsection{Orchestration Errors}

Orchestration errors arise in the control flow logic that governs agent execution, particularly in multi-agent systems where coordination between agents introduces additional complexity.

\begin{itemize}
  \item \textbf{Infinite Loop:} The agent enters a cycle of repeated actions without making progress toward the goal, often caused by ambiguous termination conditions.
  \item \textbf{Wrong Branch:} In graph-based orchestration, the agent follows an incorrect execution path due to faulty routing logic or misinterpreted state.
  \item \textbf{State Corruption:} Shared state between agents or between execution steps becomes inconsistent, leading to incorrect behavior.
  \item \textbf{Missing Handoff:} In multi-agent systems, a required handoff between agents fails to occur, leaving tasks incomplete.
\end{itemize}

\subsection{Context Degradation}

Context degradation failures relate to the finite context window of LLMs and the challenge of maintaining coherent state across long interactions.

\begin{itemize}
  \item \textbf{Window Overflow:} The accumulated context exceeds the model's maximum token limit, causing truncation of earlier information that may be critical for task completion.
  \item \textbf{Lost State:} Important information from earlier in the conversation is effectively forgotten, even when technically within the context window, due to attention dilution.
  \item \textbf{Hallucinated History:} The agent fabricates events or tool results that never took place, confabulating a history that diverges from reality.
\end{itemize}

\subsection{Latency Anomalies}

Latency anomalies are performance degradation patterns that do not cause outright failures but can still hurt usability and reliability in production.

\begin{itemize}
  \item \textbf{P99 Spike:} Tail latency increases dramatically for a subset of requests, often due to complex reasoning chains or large context processing.
  \item \textbf{Cascading Delay:} A slow response from one component propagates through the agent pipeline, amplifying the total response time.
  \item \textbf{Cold Start:} Initial requests after deployment or scaling events experience significantly higher latency.
  \item \textbf{Jitter:} Response times exhibit high variance, making it difficult to set appropriate timeouts and SLAs.
\end{itemize}

\subsection{Output Consistency Violations}

Output consistency violations address the non-deterministic nature of LLM-based agents, where identical inputs may produce semantically different outputs across executions.

\begin{itemize}
  \item \textbf{Non-deterministic Outputs:} Given the same input and tool responses, the agent produces different final answers or takes different action sequences across runs, complicating testing and validation.
\end{itemize}

\Cref{tab:taxonomy} summarizes the taxonomy with the number of sub-types per category and the corresponding \agentprobe{} component that addresses each.

\paragraph{Scope of the empirical evaluation.} The taxonomy is a theoretical contribution intended to guide future fault-injection research across all five categories. The experiments in this paper evaluate only the \emph{tool call faults} category (four sub-types), which we prioritize because tool calls are the primary interaction boundary between agents and external systems and the most common failure surface reported in production incident discussions. Injectors for orchestration errors and context degradation are implemented in the toolkit but have not been experimentally validated; latency anomalies are observed rather than injected; and output consistency is detected by a classifier only. Extending the empirical evaluation to additional categories is the most important direction for future work.

\section{System Architecture}\label{sec:system}
% ============================================================================

\agentprobe{} is designed as a modular Python toolkit with three core layers: fault injection, observability, and benchmarking.

\subsection{Fault Injection Layer}

The fault injection layer provides four injector modules, one for each injectable failure category (consistency violations are detected but not injected, as they arise from inherent model non-determinism).

Each injector is implemented as a Python class that wraps the target component (e.g., a tool function or orchestration step) and injects failures with a configurable probability $p \in [0, 1]$. Because injection is probabilistic, we can run statistical analyses across many runs without sacrificing realistic failure patterns.

\begin{lstlisting}[caption={Example: Injecting tool call failures with configurable probability.},label={lst:injector}]
from agentprobe.injector import ToolFailureInjector

injector = ToolFailureInjector(
    failure_type="timeout",
    probability=0.3,
    timeout_seconds=30.0
)

# Wrap an existing tool function
@injector.wrap
def search_web(query: str) -> str:
    return api_client.search(query)
\end{lstlisting}

\paragraph{Tool Failure Injector.}
Simulates API timeouts (via \texttt{time.sleep} or \texttt{TimeoutError}), malformed outputs (by corrupting the return value), rate limit responses (via \texttt{RateLimitError} exceptions), and generic API errors.

\paragraph{Orchestration Failure Injector.}
Injects infinite loop conditions (by manipulating termination flags), wrong branching (by altering routing decisions), state corruption (by modifying shared state dictionaries), and missing handoffs (by dropping inter-agent messages).

\paragraph{Context Failure Injector.}
Simulates context window overflow (by padding the context with filler tokens), lost state (by selectively removing earlier messages), and hallucinated history (by inserting fabricated tool results).

\paragraph{Latency Failure Injector.}
Introduces controlled delays to simulate P99 spikes (large random delays), cascading slowdowns (progressively increasing delays), cold start latency (high initial delay that decreases), and jitter (random delay variance).

\subsection{Observability Layer}

The observability layer provides distributed tracing and metrics collection using the OpenTelemetry standard~\cite{opentelemetry2024}. It consists of two components:

\paragraph{Tracer.}
The \texttt{AgentTracer} class instruments agent execution with OpenTelemetry spans, capturing:
\begin{itemize}
  \item Tool call invocations, arguments, and return values
  \item LLM API calls with token counts and latency
  \item Orchestration transitions (state changes, agent handoffs)
  \item Injected failures (type, timing, and recovery outcome)
\end{itemize}

Traces are exported via OTLP (OpenTelemetry Protocol) to backends such as Jaeger for visualization and analysis.

\paragraph{Failure Classifier.}
The \texttt{FailureClassifier} analyzes completed agent traces and classifies observed failures according to the taxonomy in \Cref{sec:taxonomy}. Classification is rule-based, matching exception types and trace patterns to failure categories. This enables automated aggregation of failure statistics across experiment runs.

\subsection{Benchmark Layer}

The benchmark layer provides standardized tasks and evaluation metrics for reproducible agent assessment.

\paragraph{Task Suites.}
Three task suites cover the primary capabilities of LLM-based agents:

\begin{itemize}
  \item \textbf{Tool Use} (5 queries): tasks requiring the agent to select and invoke appropriate tools, ranging from simple lookups to multi-step tool chains involving web search and calculation.
  \item \textbf{Retrieval-Augmented Generation} (5 queries): questions that require retrieving information from a document corpus covering agent reliability topics before generating an answer.
  \item \textbf{Multi-Agent Coordination} (5 queries): scenarios requiring a researcher--analyst pipeline to collaborate, with the researcher retrieving information and the analyst synthesizing results.
\end{itemize}

\paragraph{Metrics.}
\agentprobe{} computes the following metrics for each experiment run:

\begin{itemize}
  \item \textbf{Fault-Triggered Error Rate ($ER$):} Fraction of runs in which the initial \texttt{agent.invoke()} call raised an unhandled exception. This metric captures whether the agent survived the injected fault, \emph{not} whether the response was factually correct (correctness grading is available via the toolkit's \texttt{ResponseGrader} but is not used in the present study).
  \item \textbf{Mean Completion Time ($\bar{T}$):} Average wall-clock time per task.
  \item \textbf{Recovery Rate ($RR$):} Fraction of injected failures from which the agent successfully recovers.
  \item \textbf{Token Efficiency ($\eta$):} Ratio of useful output tokens to total tokens consumed.
  \item \textbf{Failure Cascade Depth ($D$):} Number of subsequent failures triggered by an initial injected fault.
  \item \textbf{Consistency Score ($C$):} Semantic similarity between outputs across repeated runs of the same task (measured via embedding cosine similarity).
\end{itemize}

\noindent The present study focuses on $ER$, $\bar{T}$, and $RR$. The remaining metrics ($\eta$, $D$, $C$) are implemented in the toolkit but are not reported here.

\paragraph{Benchmark Runner.}
The \texttt{BenchmarkRunner} orchestrates experiment execution, managing the lifecycle of injectors, tracers, and task evaluation. It supports configurable parameters including the number of runs per condition, failure injection probability, and framework selection.

\section{Experimental Methodology}\label{sec:experiments}
% ============================================================================

\subsection{Frameworks Under Test}

We evaluate three agent-oriented frameworks that represent distinct architectural approaches:

\begin{itemize}
  \item \textbf{LangGraph}~\cite{langgraph2024}: A stateful, graph-based orchestration framework where agent behavior is defined as a directed graph of nodes (actions) and edges (transitions). Supports cycles, conditional branching, and persistent state.

  \item \textbf{LangChain}~\cite{langchain2023}: A composable chain-based framework where agent behavior is defined as a sequence of processing steps. Provides high-level abstractions for common patterns (ReAct, tool use).

  \item \textbf{AutoGen}~\cite{wu2023autogen}: A conversational multi-agent framework where agents interact through structured message passing. Supports flexible agent roles and conversation patterns.
\end{itemize}

\subsection{Experimental Setup}

All experiments use the following configuration:

\begin{itemize}
  \item \textbf{LLM Backend:} Llama~3.1 8B (Q4\_K\_M quantization) served locally via Ollama~0.31.1.
  \item \textbf{Hardware:} Apple M-series, 16\,GB RAM, macOS~15.
  \item \textbf{Runs per Condition:} 30 independent runs for LangGraph and LangChain; 10 for AutoGen (constrained by its multi-turn protocol overhead, which makes each run 7$\times$ slower on average). Each \emph{run} is a single \texttt{agent.invoke()} call with one query; the runner cycles through five queries per task type using round-robin assignment ($\mathit{run\_id} \bmod 5$).
  \item \textbf{Response Caching:} pyautogen~0.1.14 caches LLM responses via \texttt{diskcache} by default; the cache is cleared before each invocation to ensure all runs reflect real inference.
  \item \textbf{Failure Injection Probability:} $p = 0.20$ for timeout and malformed output; $p = 0.15$ for rate limit and API error. The random seed (42) controls the injection sequence; the LLM itself introduces stochastic variation across runs because Ollama does not fix a sampling seed, so repeated runs produce different model outputs.
  \item \textbf{Error Detection:} A run is recorded as an \emph{error} if the initial \texttt{agent.invoke()} call raises an unhandled exception. The toolkit includes a keyword-matching \texttt{ResponseGrader} for correctness assessment, but correctness grading is not used in the error-rate analysis reported here.
  \item \textbf{Run Timeout:} Each \texttt{agent.invoke()} call is subject to a 60-second wall-clock timeout. Runs exceeding this limit raise a \texttt{Timeout} exception and are recorded as errors.
  \item \textbf{Recovery Procedure:} After a failed run (unhandled exception), the harness immediately retries \texttt{agent.invoke()} once with the same input (\texttt{recovery\_attempts\,=\,1}). No backoff is applied. The fault injector remains active during the retry, so the retry may also encounter an injected fault (with the same per-call probability). A run is marked as \emph{recovered} if the retry completes without exception. This measures resilience at the harness level, not framework-internal retry logic.
  \item \textbf{Task Suites:} All three suites---tool use, RAG, and multi-agent---each containing 5 benchmark queries (15 total).
  \item \textbf{Failure Types:} Each tool call fault sub-type (timeout, malformed output, rate limit, API error) injected independently, plus a no-injection baseline.
\end{itemize}

\subsection{Experimental Conditions}

We define the following experimental conditions for each framework:

\begin{enumerate}
  \item \textbf{Baseline} ($C_0$): No fault injection. Establishes the framework's performance under ideal conditions.
  \item \textbf{Timeout Injection} ($C_1$): Tool calls may time out with probability $p$.
  \item \textbf{Malformed Output Injection} ($C_2$): Tool calls may return malformed responses with probability $p$.
  \item \textbf{Rate Limit Injection} ($C_3$): Tool calls may return rate limit errors with probability $p$.
  \item \textbf{API Error Injection} ($C_4$): Tool calls may return generic API errors with probability $p$.
\end{enumerate}

This yields $3 \times 5 = 15$ experimental conditions per framework, for a total of $15 \times 30 + 15 \times 30 + 15 \times 10 = 1{,}050$ experiment runs across all three frameworks.

\subsection{Statistical Analysis}

We report 95\% confidence intervals for all metrics: Wilson score intervals for proportions (error rate, recovery rate) and $t$-distribution intervals for continuous measures (latency). Pairwise comparisons between frameworks use the chi-squared test with Yates' correction for proportions, and the Kruskal--Wallis $H$ test as an omnibus test for latency distributions. Effect sizes are reported using Cohen's $h$ for proportions.

\section{Results}\label{sec:results}
% ============================================================================

A total of 1{,}050 experiment runs were completed across all conditions. Full results data and analysis scripts are available in the project repository. \Cref{fig:dashboard} summarizes the main findings.

\begin{figure}[htbp]
  \centering
  \includegraphics[width=\textwidth]{plots/summary_dashboard.png}
  \caption{Summary dashboard showing cross-framework reliability comparison: (a)~fault-triggered error rate under injection (baseline excluded), (b)~recovery rate under injection conditions, (c)~mean baseline latency (no injection), and (d)~P99 baseline latency by task type. \subsection{Baseline Performance}

Under baseline conditions (no fault injection), LangGraph and LangChain both achieve a 0\% error rate [95\%~CI: 0.0--4.1\%, $n = 90$ each]. Mean latency varies by task: tool use is fastest (LangGraph: 6.1\,s, LangChain: 6.0\,s), followed by RAG (LangGraph: 8.0\,s, LangChain: 11.4\,s) and multi-agent coordination (LangGraph: 11.7\,s, LangChain: 10.7\,s).

AutoGen exhibits a 16.7\% baseline error rate [95\%~CI: 7.3--33.6\%, $n = 30$], with all five failures occurring in the multi-agent task (5/10 runs), while tool use and RAG complete without errors. All baseline failures are Timeout exceptions caused by the multi-turn conversation protocol exceeding the allowed execution time when running on local Llama~3.1 inference. AutoGen's mean baseline latency is 62.5\,s---7$\times$ higher than LangGraph (8.6\,s)---ranging from 34.0\,s for tool use to 105.2\,s for multi-agent tasks.

\subsection{Fault Tolerance Comparison}

\begin{figure}[htbp]
  \centering
  \includegraphics[width=\textwidth]{plots/failure_rate_by_framework.png}
  \caption{Fault-triggered error rate by framework and injection type. LangGraph and LangChain show matched error rates under all injection conditions. AutoGen shows lower injection error rates due to tool-execution bypass, but exhibits failures under the ``None'' (baseline) condition from conversation-protocol timeouts. Error bars omitted for clarity; 95\% Wilson score CIs are reported in the text.}\label{fig:sr_comparison}
\end{figure}

Under fault injection, LangGraph and LangChain both exhibit a fault-triggered error rate of 16.1\% [95\%~CI: 12.7--20.3\%], with 58 errors (unhandled exceptions on the first invocation attempt) out of 360 injection runs each (baseline runs excluded from the denominator). Timeout and malformed output injection produce error rates of 16.7\% [10.4--25.7\%], while rate limit and API error injection yield 15.6\% [9.5--24.4\%]. The difference between LangGraph and LangChain is not statistically significant ($\chi^2$ test with Yates' correction, $p = 1.0$, Cohen's $h = 0.000$, negligible effect). This reflects a shared implementation: in LangChain~1.3 (the version tested here), \texttt{create\_react\_agent} delegates to LangGraph for agent execution, making them architecturally equivalent at the tool-calling layer.

AutoGen shows a 5.8\% error rate under injection [95\%~CI: 2.9--11.6\%, $n = 120$], but this lower rate reflects tool-execution bypass (\Cref{sec:autogen-silent}), not superior fault tolerance. All AutoGen failures are conversation-protocol Timeout exceptions, unrelated to the injected faults. Within multi-agent tasks, the baseline failure rate (5/10 = 50\%) exceeds the injection rate (5/40 = 12.5\%; Fisher's exact $p = 0.018$), but with only $n = 10$ baseline runs and no multiple-testing correction across the 15 conditions tested, this difference is consistent with sampling noise around the pooled multi-agent rate of 20\% (10/50). AutoGen's overall error rate of 8.0\% [4.6--13.5\%] is therefore driven by stochastic protocol timeouts that occur independently of injection condition.

\subsection{The Silent Failure Phenomenon}\label{sec:autogen-silent}

A closer look at the AutoGen traces reveals why the injection error rate is low. pyautogen~0.1.14 sends tool definitions using the legacy \texttt{functions} parameter in the chat completion request, which Ollama's OpenAI-compatible endpoint does not honor. As a result, Llama~3.1 never receives the formatting cue it needs to emit a tool-call JSON block; it answers every query from parametric knowledge alone, and the fault injectors---which wrap the tool functions---are never triggered. This is an \emph{ecosystem integration bug}---a mismatch between the client library's API schema and the inference server's supported parameters---not an inherent property of AutoGen's conversational architecture. It explains the 0\% error rate for tool use and RAG tasks under all injection conditions.

Separately, AutoGen exhibits conversation-protocol timeouts that affect multi-agent tasks regardless of injection condition. These timeouts arise because the \texttt{initiate\_chat} protocol exchanges up to \texttt{max\_turns} messages with local Llama~3.1 inference, and multi-agent queries---which tend to elicit longer, multi-paragraph responses---frequently exceed the execution time limit. This is an \emph{architectural limitation} of the multi-turn protocol when paired with slow inference. Together, the dual failure pattern (integration-level tool bypass + architecture-level protocol timeouts) would be invisible without trace-level observability: the tool bypass makes injected faults appear harmless, while the protocol timeouts manifest identically under baseline and injection conditions. \agentprobe{}'s observability layer detects both through tool invocation counts and per-turn latency spans in the trace data.

\section{Discussion}\label{sec:discussion}
% ============================================================================

\subsection{Why LangGraph and LangChain Converged}

The identical failure counts ($p = 1.0$) were not the result we expected when we began this study. We initially chose LangChain and LangGraph because they advertise different programming models---chains versus graphs---and we anticipated at least some divergence in fault tolerance. The trace data explained the convergence: in LangChain~1.3 (the version tested), \texttt{create\_react\_agent} delegates tool dispatch to LangGraph under the hood, so both frameworks execute the same retry-and-fallback logic at the tool-calling boundary. The identical counts extend to recovery outcomes because the fixed seed (42) produces the same injection sequence in both frameworks, and recovery is determined by the shared retry logic rather than by model stochasticity. A more informative comparison would have been a pre-LangGraph version of LangChain (using the now-deprecated \texttt{AgentExecutor}) against LangGraph. This highlights a broader lesson for benchmarking: framework APIs can be misleading proxies for architectural difference.

\subsection{What AutoGen's Silent Failure Means in Practice}

AutoGen's low injection error rate (5.8\% vs 16.1\% for LangGraph/LangChain) initially appeared to suggest superior fault tolerance. Trace analysis revealed two co-occurring issues---one an ecosystem integration bug, the other an architectural limitation---that make this comparison misleading.

The first issue is an \emph{integration bug}, not a property of conversational multi-agent design. pyautogen~0.1.14 sends tool definitions using the legacy \texttt{functions} parameter, which Ollama's OpenAI-compatible endpoint silently ignores. Llama~3.1 never receives the formatting cue it needs to emit a tool-call JSON block, so it answers every query from parametric knowledge and the fault injectors sit idle. This is a version-specific API-schema translation failure between the client library and the inference server; a different serving stack (e.g., one that honors \texttt{functions} or uses the newer \texttt{tools} parameter) or a newer client release would likely restore tool calling and expose AutoGen to the same injected faults as LangGraph/LangChain.

The second issue is an \emph{architectural limitation}: AutoGen's multi-turn conversation protocol, in which the \texttt{UserProxy} and \texttt{AssistantAgent} exchange up to \texttt{max\_turns} messages, introduces cumulative latency that frequently exceeds the execution time limit when backed by local LLM inference. This produces a 16.7\% baseline error rate---higher than LangGraph/LangChain's error rate \emph{under active fault injection}. Unlike the tool bypass, this failure mode is inherent to the conversation protocol and would persist regardless of the serving stack, though faster inference hardware would reduce its frequency.

Both issues would be invisible without trace-level observability: the tool bypass inflates success-rate metrics, while the protocol timeouts may be attributed to model slowness rather than protocol overhead. The fix requires tool-invocation auditing and per-turn latency tracing---capabilities that most evaluation harnesses do not provide. We built both into \agentprobe{} because we encountered these problems during pilot experiments.

\subsection{Error Signals and Recovery}

The gap between rate-limit/API-error recovery (86\%) and timeout/malformed-output recovery (73\%) has a concrete explanation rooted in how the harness retry interacts with injection probability. Our recovery procedure re-invokes \texttt{agent.invoke()} once with the fault injector still active. Rate-limit and API-error conditions use a 15\% injection probability, giving the retry an 85\% chance of a clean tool call; timeout and malformed-output conditions use 20\%, reducing the clean-call probability to 80\%. This probability gap accounts for most of the observed recovery difference. Additionally, timeout injection imposes a 5-second delay on the failed call, leaving less headroom within the 60-second run timeout for a successful retry. Agent middleware should normalize all tool failures into a common error envelope (status code, retry hint, partial result) so that the LLM and the orchestrator can make informed recovery decisions rather than silently propagating bad data.

\subsection{Implications for Hybrid Architectures}

The failure modes we catalogued map surprisingly well onto the classical distinction between symbolic and sub-symbolic agents. Orchestration errors (infinite loops, wrong branches) are precisely the kind of problem that BDI-style goal management was designed to prevent: explicit plan libraries and intention-reconsideration give the agent a principled way to abandon a failing plan. Context degradation, similarly, is less of a concern when state is maintained in a logical database rather than in an LLM's attention window.

Where LLM-based agents clearly win is flexibility: they can handle ambiguous natural-language queries and use tools they were not explicitly programmed for. A practical hybrid might use a BDI planner to manage high-level goals and enforce tool-invocation requirements (preventing AutoGen-style bypass), while delegating individual tool calls and natural-language reasoning to the LLM. \agentprobe{}'s fault injectors could serve as a regression suite for such a system, verifying that the BDI layer actually catches the failure modes it is supposed to guard against.

\subsection{Limitations}

\begin{itemize}
  \item Our study evaluates three frameworks; results may not generalize to all agent architectures (e.g., CrewAI, DSPy).
  \item \textbf{Taxonomy--evaluation gap:} The taxonomy defines five failure categories, but the current experiments inject only tool call faults---the category we consider most practically urgent. Orchestration and context injectors are implemented in the toolkit but have not been experimentally validated; latency anomalies are observed rather than injected; consistency violations are detected by a classifier only. This means the paper's empirical claims are scoped to tool-call resilience; whether the remaining categories produce similar cross-framework patterns is an open question.
  \item Fault injection probabilities are uniform ($p = 0.15$--$0.20$); production failure patterns may be bursty or correlated.
  \item We use a single LLM backend (Llama~3.1 8B); larger models or commercial APIs (GPT-4, Claude) may exhibit different resilience characteristics, particularly for tool-calling format compliance.
  \item The convergence of LangChain and LangGraph is version-specific (LangChain~1.3, the version tested); earlier versions using the deprecated \texttt{AgentExecutor} may show different behavior.
  \item AutoGen's tool-execution bypass is specific to the pyautogen~0.1.14 + Ollama combination; the community fork (AG2) and Microsoft's AutoGen~0.4 rewrite may handle local models differently.
\end{itemize}

\subsection{Threats to Validity}

\paragraph{Internal Validity.} The use of controlled fault injection with fixed probabilities and a fixed seed (42) ensures reproducibility but may not capture the complexity of real-world failure patterns. We mitigate this by using 10--30 runs per condition and reporting Wilson score confidence intervals. With 30 runs cycling through 5 queries via round-robin, each query repeats 6 times, so runs using the same query are not fully independent. We treat this as acceptable for measuring infrastructure-level error rates (which depend on injection timing, not query content) but note it as a limitation for any future correctness analysis.

\paragraph{External Validity.} Our benchmark tasks are designed to be representative but cannot cover all possible agent applications. We select tasks that exercise the core capabilities (tool use, RAG, multi-agent coordination) common to most production deployments. Critically, all experiments use a locally hosted open-weight model (Llama~3.1 8B via Ollama on an Apple M-series laptop with 16\,GB RAM). This runtime lacks constrained decoding and server-side JSON enforcement, which cloud-hosted frontier APIs (GPT-4o, Claude~3.5 Sonnet) typically provide. Frameworks that depend on reliable structured output---including tool-call JSON formatting---may exhibit different failure profiles when backed by a cloud API that enforces output schemas. Our findings are therefore most directly applicable to local, unconstrained open-weight inference runtimes; generalization to cloud-hosted endpoints requires separate validation.

\paragraph{Asymmetric Sample Sizes.} AutoGen was evaluated with $n = 10$ runs per condition versus $n = 30$ for LangGraph and LangChain, because AutoGen's multi-turn protocol makes each run approximately 7$\times$ slower (mean 62.5\,s vs 8.6\,s). This asymmetry substantially widens AutoGen's confidence intervals: the Wilson score CI for the 16.7\% baseline rate spans [7.3\%, 33.6\%] (width 26\,pp), compared to widths of $\sim$15\,pp at $n = 90$. An exact binomial power analysis at $\alpha = 0.05$ shows that $n = 10$ achieves 80\% power only for differences exceeding $\sim$43 percentage points from the LangGraph/LangChain injection rate (16.1\%), meaning small-to-moderate effects would go undetected. We accept this trade-off against the 7$\times$ per-run cost and report all CIs explicitly so that readers can assess precision directly.

\paragraph{Construct Validity.} Our metrics (fault-triggered error rate, recovery rate, latency) are standard in reliability engineering but may not capture all dimensions of agent quality (e.g., answer correctness is not assessed). We supplement quantitative metrics with qualitative trace analysis.

\section{Conclusions and Future Work}\label{sec:conclusion}
% ============================================================================

The central lesson from our experiments is that a passing score on an agent benchmark does not mean the agent is working correctly. AutoGen exhibited a lower error rate than LangGraph/LangChain under fault injection---not because it handled faults better, but because an API-schema mismatch between the client library and the inference server silently prevented tool execution. At the same time, its multi-turn conversation protocol produced the highest baseline failure rate of all three frameworks due to cumulative latency exceeding run timeouts. Without trace-level observability, we would have reported the injection-only numbers at face value and drawn the wrong conclusion. Similar integration-level silent failures likely exist in other framework--model--server combinations that have not yet been tested with fault injection; \agentprobe{} is designed to make that kind of testing straightforward to set up.

The toolkit, the failure taxonomy, and the full experimental data are available at \url{https://github.com/chhayankjain/AgentProbe}. We encourage other groups to run \agentprobe{} against their own framework and model combinations, and to contribute new injector modules for failure modes we have not yet covered.

\paragraph{Future Work.}
The most pressing open question from our study is whether the tool-bypass integration bug extends to other local-model serving stacks (vLLM, TGI, llama.cpp's server mode) and to newer client releases (the AG2 community fork and Microsoft's AutoGen~0.4 rewrite). A targeted follow-up with those configurations would clarify whether the \texttt{functions}-parameter mismatch is specific to the pyautogen~0.1.14--Ollama pairing or a recurring integration hazard across conversation-based frameworks and local inference servers. Equally important, the current experiments evaluate only one of our five taxonomy categories (tool call faults); experimentally validating the orchestration-error and context-degradation injectors is a high priority.

Beyond that, two directions interest us most. First, our fault injection probabilities are uniform and independent; real production failures tend to be bursty and correlated (e.g., a rate-limit storm that triggers cascading timeouts). Building a correlated-failure injector and measuring how recovery rates change would bring \agentprobe{}'s fault model closer to production reality. Second, the gap between timeout recovery (73\%) and rate-limit recovery (86\%) suggests that a simple middleware layer---one that wraps every tool call in a typed error envelope with a retry hint---could substantially improve resilience. We plan to prototype this wrapper and measure whether the recovery gap narrows.
